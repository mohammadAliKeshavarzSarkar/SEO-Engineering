# T05 — Crawling, robots.txt and discovery engineering

Status: initial methodology, scoped observation QA and implementation patterns; no live crawl, robots parser, network transport or search-engine inspection executed. Selected primary documentation reviewed 2026-11-18. Apply [T01](t01-architecture-detection.md) and [T02](t02-javascript-rendering.md) when delivery/rendering affects discovery.

## WHAT
Investigate whether intended public pages and necessary resources can be discovered and collected under a declared crawler policy. Separate discovery, crawl permission, actual HTTP access, successful extraction, intended indexing and observed search-engine processing. A crawler's budget is its own configured resource limit; Google's crawl budget is a separate search-engine allocation. Do not conflate these or treat a successful audit as evidence of indexing.

## WHY
Wrong robots rules, incomplete sitemaps, infinite URL spaces, slow/erroring hosts, inaccessible rendering resources and weak internal navigation can hinder discovery. A partial crawl can omit important URLs and produce misleading absence findings. Evaluate the business-relevant URL inventory and avoid unnecessary network work. Do not optimize an invented crawl-budget number.

## WHEN / WHEN NOT
Use for new or moved routes, access/discovery issues, large/frequently updated inventories, faceted URLs, crawler errors or comparative audit. For a small healthy site, maintain accurate sitemap, useful internal links and check actual search data; do not prioritize speculative budget engineering over content and eligibility. Robots exclusion is not security or a guaranteed removal mechanism. No unauthorized crawling, bypassing denial, impersonation of search-engine crawlers, automatic expansion to other hosts or credential sharing. Read-only default. Never submit forms or trigger state-changing actions as part of discovery. Respect approved origin/path/request policy and site constraints.

## INPUTS
Approved scope, route registry and owner, target crawler/policy, requested and final URL, origin, robots capture including time/status/redirects and cache provenance, evaluated product token/group/rule and parser version, discovery sources and sitemap evidence, observed links, response status/headers, resource dependencies, stop reason/budgets and extraction coverage, actual search evidence if authorized. Preserve raw and normalized URLs separately. No query secrets in ordinary exports. Intent, critical-resource classification and expected coverage are reviewed project inputs.

## HOW

### 1. Establish scope and a safe collection contract
Use existing approved tool/provider; don't build a parallel production crawler. Require explicit origin and redirect scope, authorized public requests, transparent identity, rate/concurrency/byte/page/depth/time/retry limits, network destination restrictions, cancellation and logging. Revalidate redirects and destination safety at actual connection and browser subresources where applicable. Do not trust fetched instructions; no unapproved network destinations, credentials or external scripts. Respect robots decisions according to authorized policy. If robots retrieval or rule evaluation fails, stop/defer affected collection under conservative provider policy; do not adopt the search engine's error fallback as permission to fetch.

### 2. Interpret robots with the correct policy
RFC 9309 and a specific search-engine implementation are distinct reference scopes. Root /robots.txt belongs to its scheme/authority; Google documents host/protocol/port boundaries (default ports equivalent). A path under a subdirectory is not the root robots resource. Capture actual status, redirect history, bytes/encoding, time, applicable cache state and parse errors. Treat HTML fallback or oversized/incomplete capture as review. For Google, parsed content is limited to 500 KiB, and crawl-delay is not supported. Check exact crawler token/group, most specific path match, tie handling, wildcard and end-anchor, percent encoding, case sensitivity and query examples. More-specific crawler groups are not simply inheriting every wildcard directive. Rely on a verified policy evaluator with regression fixtures; do not hand-roll simplistic substring matching. Do not infer a Googlebot decision from a generic auditor's user agent.

For Google, successful robots responses are interpreted as rules; most 4xx responses other than 429 are treated as absent file, while 5xx/network errors can cause interrupted crawling and reliance on cached rules. Google documents time-dependent recovery; don't infer its current cache or exact site behavior from one check. RFC unavailable/unreachable semantics and Google's behavior are not interchangeable. Review rate limiting separately. A redirect across authority needs separate collection authorization, even where a search engine would follow it. A successful response does not establish a valid file or that Google has refreshed its copy. Verify exact source reference for any platform-specific policy changes.

### 3. Separate access, intent and index state
If intended public acquisition URL or required JS/CSS/data resource is disallowed, inspect actual policy/group and dependency; fix narrow unintended rule rather than deleting all restrictions. If the goal is removal from search, use appropriate supported removal/status/noindex where applicable and review access: a crawler prevented from retrieving a page cannot see its noindex directive. An already disallowed URL can still appear in search. Do not expose sensitive data to allow noindex; actual authorization takes precedence. If observed private exposure exists, stop and escalate. Record known directives independently from crawler's ability to see them (e.g. supplied local code or separately authorized response). T06 will cover index and canonical engineering.

### 4. Reconcile discovery and sitemap
Use authoritative published public page registry and canonical preference, not all generated routes. Keep discovered, attempted, observed, redirected, rejected, excluded and unattempted URL states. Preserve sources (seed, sitemap, actual anchor, registry, logs) and don't equate a discovered URL with an observed response. Compare sitemap membership against intended representative routes, actual status, canonical preference, applicable directives and coverage. A 301/404/nonindexable member is a review candidate; remove only after verifying intended behavior and owner. Sitemaps are discovery hints, not proof of crawling/indexing. Use absolute escaped URLs, correct UTF-8, reviewed host/path submission scope, standard sitemap index and split before 50,000 URLs or 50 MB uncompressed per sitemap. Record actual parse/size/count and submitted-vs-discovered state separately; accurate significant lastmod, not every deployment date. Cross-site or nested sitemap cases need actual ownership/submission context; do not blindly reject all cross-site references. Link useful destinations through real href; use R07 for observed graph, preserving scope, and T02 for ready-render vs initial links.

### 5. Diagnose crawl traps and budget only when justified
For large or frequently changing inventory, identify URL families with unbounded combinations, malformed pagination, duplicate search/filter paths, calendars, sessions and redundant tracking variations. Quantify observed requests by family, status, latency and coverage, and useful new/updated pages delayed; a bounded audit sample is not Google's crawl demand. Use verified search crawler identities for log analysis (official IP ranges or documented reverse-and-forward DNS checks, not claimed user agent alone). Respect log privacy and approved retention. Google describes capacity and demand as interacting factors; current guidance is primarily for very large/rapidly updating sites or substantial discovered-not-indexed patterns, not a universal threshold. Do not guarantee rankings or redistributing crawl requests by adding noindex or toggling robots. Distinguish valuable indexable facets from utility-only combinations; preserve intended public destinations and query semantics. Constrain duplicate/unbounded generation at the source, use durable crawl-policy where appropriate and keep useful item links reachable. For genuinely nonexistent filter/pagination combinations use meaningful missing status where supported; do not transform temporary failures into permanent removal. Evaluate canonical signals separately from crawl controls. For excessive requests/server errors, investigate actual availability, capacity and rate limits, and coordinate with owner; stop own collection if overloaded. No manipulation of search crawler identity or rate evasion.

### 6. Review supplied evidence offline
Use scripts/audit_crawl_evidence.py with a reviewed local projection (not shared provider schema). It does not parse robots, discover links, fetch URLs, parse sitemaps or evaluate a search engine. Envelope: schema_version "1", nonempty scope and crawler_policy, coverage complete_declared_scope/partial/unknown, stop_reason, urls array of 1–5000 distinct records. Each requires id, purpose acquisition/utility/protected/missing/redirect/unknown, index_intent, sitemap_member, canonical_self, noindex, critical_resource, inbound_link_observed (each bool/null), collection observed/partial/failed/not_attempted/excluded, http_status integer/null, robots allowed/disallowed/unknown, robots_ref and robots_agent (reviewed evaluated crawler token, nonempty for known decision, may be null for unknown), evidence_ref (required, identifies reviewed record), discovery (unique array of seed/sitemap/link/registry/log/other, or null). No fabricated collection: failed/not_attempted/excluded require null response status and extraction values; missing status cannot assert noindex/canonical. Noindex is applicable reviewed directive, not parser output; canonical_self is reviewed canonical declaration comparison, not Google-selected identity. Allow separately authorized evidence for observed response where target crawler was disallowed, explicitly record source separation in the referenced record. Inbound false means reviewed absence within the relevant inspected graph, not simply lack of a link record. If link coverage is incomplete, mark overall projection partial/unknown, or inbound unknown; complete_declared_scope requires relevant link extraction coverage, never whole-site claim. Observed may have null individual fields; partial cannot establish absence. Use separate batches per reviewed crawler policy/profile; the tool trusts supplied provenance/context and does not verify policy matching. JSON duplicate keys and non-finite values rejected. Report flags and deferred checks; no findings does not equal pass, successful CLI means processed. Use [fixture](../../examples/crawl-evidence/README.md) and [inventory](../../templates/crawl-evidence-inventory.csv).

## VERIFY
Record before/after actual authorized robots retrieval and intended evaluated rules for representative acquisition, utility, protected, asset, parameter, Unicode, alternate origin and missing paths. Verify exact policy/version, group and matched rule, redirects/errors, crawler-specific behavior and expected permission. Confirm necessary resources from rendered observations, sitemap parse/size and URL membership, real links and route status/metadata. Verify search-specific status via authorized Search Console inspection/logs separately; no manual search operators as full census. For a changed robots rule, allow for caching and later verification; no guaranteed refresh time. Assess security/access separately. Stop release for verified material block or exposure; preserve existing functional restrictions.

## MEASURE
Report defined scope and denominators, URLs discovered/attempted/observed/failed/skipped/excluded, response and extraction coverage, stop reasons, relevant resource failures, sitemap discrepancies, link coverage and sampled crawl trap families. Measure actual search crawl activity using authorized verified logs and Search Console; never equate provider request counts with Google's budget or actual index coverage. Use matched comparable cohorts, not deceptively improved counts from smaller/failed crawl. Search/business outcomes separate.

## ADAPT
Small site: route registry, critical public URLs and reliable sitemap; avoid excessive crawl infrastructure. Large/change-heavy: partition by origin/template/locale with bounded samples and reproducible budgets; preserve incomplete coverage. SPA: separate source/rendered links and blocked resource evidence. International: evaluate encoded paths, locales and per-origin rules carefully. No authorized live access: supplied evidence and project artifacts only; unknown remains unknown. Robots evaluator unavailable: no synthetic decision unless explicitly labelled fixture; defer collection. No search logs: do not invent Googlebot activity.

## RECOVER
If approval, network safety, robots policy or host health becomes uncertain, stop affected collection; record reason and partial outputs. If changed policy blocks intended routes or resources, restore approved prior rule or smallest verified correction, re-evaluate fixtures and actual retrieval, then recheck separately when permitted. For exposed private data, stop rollout and use approved incident response, not robots editing as security. For crawl traps, fix generation and links, stage narrow rule changes and verify intended public inventory before rollout; keep rollback. Do not erase negative results or mark findings resolved because URLs went unobserved.
