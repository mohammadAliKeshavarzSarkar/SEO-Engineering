# T07 — URL architecture and migration engineering

Status: initial methodology and offline mapping/trace QA. No live migration, redirects, DNS changes, crawl or independent behavioral evaluation performed. Selected primary sources reviewed 2026-11-18. Prerequisites: [T05 crawl evidence](t05-crawling-robots.md), [T06 canonical engineering](t06-indexing-canonicals.md), [R06 page ownership](../02-research/r06-keyword-to-page-mapping.md) and [R09 localization](../02-research/r09-multilingual-search-engineering.md).

## WHAT
Design durable public URL identities and preserve useful existing destinations across redesigns, CMS/framework moves, path/domain changes, consolidations and infrastructure changes. Separate requested/discovered URL, normalization key, actual redirect hops, final URL, content identity and intended canonical. A rewrite changes internal routing without necessarily changing public URL; a redirect sends the user agent to another URL. Neither is the same as a canonical preference.

## WHY
A visually better or technically faster replacement may lose existing discovery, links, attribution or useful localized destinations if URL behavior changes indiscriminately. Migration is a real release with operational and business risks, not a guaranteed way to improve rankings.

## WHEN / WHEN NOT
Use for planned or observed URL changes, redirect issues, legacy routes, domain/HTTPS moves, duplicate variants and navigation changes. If redesign or infrastructure replacement can retain existing URLs, prefer preservation. Do not change slugs solely for a keyword or aesthetic preference without justified value. Do not perform real redirects, DNS, host changes, deployment, search property actions or external requests outside explicit approval. No protected content in public exports, no signed/secret URLs, and no open redirect endpoint or untrusted Host-derived destination.

## INPUTS
Approved old/new origins, release and rollback owners, exact route inventory from CMS, sitemap, analytics, verified search data/logs, links and assets, relevant query and locale policies, meaningful content equivalence, old/new runtime/host config and routing precedence, expected redirects/status, baseline performance and conversions, deployed observations with timestamps/method/profile and evidence refs, TLS/DNS and ownership readiness where applicable. Preserve source differences and unvisited records. Unknown inventory is not deleted content.

## HOW

### 1. Select the minimum change
Classify redesign/no visible URL change, hosting-only move, HTTPS/hostname change, path reorganization, domain/subdomain move, genuine merge or deletion. If possible separate domain migration from CMS, design, content and URL restructuring to isolate causes. For large sites consider controlled cohorts; for smaller sites coherent switch may be appropriate. Review operational dependencies rather than assume one rollout size.

### 2. Establish an explicit URL policy
Prefer descriptive stable paths and ordinary URL parameter syntax. Avoid fragment-only identity for independent public content; retain useful anchor fragments and client UI where appropriate. Distinguish server case sensitivity, trailing slash, host, scheme, effective port, repeated query parameters, parameter order and values, default-document rules and Unicode/percent encoding. Reserved characters encoded as data (e.g. %2F) may differ from path delimiters; do not repeatedly decode or normalize blindly. Lowercase host according to URL semantics, but never assume lowercase paths are interchangeable. Unicode/Persian display strings and UTF-8 encoded request URLs must be mapped using actual framework/browser semantics; preserve source spellings and validate encoding exactly once, including Persian/Arabic letter differences, half-space and locale routes. No automatic transliteration migration or blanket stripping/sorting of query parameters. Separate tracking params permitted for attribution from state-changing/signed/private or content-defining params; approve any transform per route, preserve meaningful repeats/order where needed. Key normalization policy must not silently change fetch URL or merge content identity. Test host variants, slashes, case, encoding, aliases and query families in actual host; no general equivalence claimed by offline checker. For new site choose consistent canonical URL registry; existing useful route continuity is primary.

### 3. Build reviewed mapping with explicit actions
Inventory actual old URLs and useful resources, with discovery provenance, baseline content/access and traffic/link relevance. Include downloads, media, deeply linked routes, old campaigns, locale routes, historical variants and old redirects. Map:
| Action | Intended behavior |
|---|---|
| retain | Same public URL delivers expected behavior |
| permanent_redirect | Direct 301/308 to a reviewed equivalent or genuinely consolidated replacement |
| temporary_redirect | Time-bounded alternative (302/307; 303 when applicable indirect response) |
| remove | Actual 404/410 for retired public content with no replacement |
| unknown | Defer pending evidence/approval |
Protected routes and action/API endpoints need independent security and method lifecycle, not automatic public migration rules. Many-to-one is legitimate only for truly consolidated relevant content. Avoid unrelated homepage or search redirects; not every old URL should have a new destination. Keep planned map separate from observed traces. Review target status, content equivalence, availability, canonical and locale. New-only routes belong to new registry. Host-wide patterns need per-family exceptions and test vectors; do not generate unreviewed regex or derive destinations from arbitrary user input.

### 4. Implement redirects and actual routing
Prefer supported server/edge HTTP redirects for approved moves. HTTP 301/302 may change POST to GET; 307/308 preserve method, 303 has indirect retrieval semantics. SEO page migration checks use GET only, do not apply to form submissions or API mutation routes without separate review. A 304 is cache validation, not a redirect to a new resource; a 300 or other 3xx is not automatically one of the followable redirect classes in this utility. Use actual Location header, including relative reference resolution and duplicate/malformed header review; preserve raw and reviewed resolved destination. Follow only authorized approved scope using existing bounded provider; never treat a Location as permission. Aim at final intended URL directly; plan and check redirect loops/chains, existing legacy rules and precedence across CDN, proxy, app and host. Protect against redirect injection, encoded bypass and open redirects; fixed vetted destinations or safe allowlisted mapping, no header/query secrets. A client route or meta refresh is last-resort alternative where server support absent; verify actual user and crawler behavior and don't label it server 301. Use valid certificates on old and new hosts and keep old origin available for redirects. Avoid redirecting assets or missing API requests to HTML. Stage protected; remove development noindex/robots blocks only from intended public production routes, maintain actual auth.

### 5. Reconcile destination signals
Update internal anchors, actual canonicals (T06), hreflang (R09), structured data URLs, sitemap, asset/download references, share links, navigation, analytics and campaign links. Generate from reviewed route registry where possible. Preserve meaningful URL and attribution params according to policy, canonical preference may intentionally exclude tracking params while actual redirect preserves them. Test locale and route purpose. Noindex is not security. Validate actual initial/full response and rendered content (T02–T04). Google Change of Address only for eligible domain/subdomain migrations after redirects; both properties must be owned in same account, verify exact requirements. Not for HTTP-to-HTTPS, www/non-www, path-only or hosting-only moves. Actual submission requires authorization. Keep redirects generally at least a year for Google site moves, longer where useful. No guaranteed transfer of ranking or timing.

### 6. Offline mapping and trace QA
Use scripts/audit_migration.py on reviewed local projection, not shared provider schema. Envelope schema_version "1", scope, policy_version, allowed_origins (1–100 explicit scheme/host/effective port, no path except slash or query), routes (1–5000). Each row: unique id and exact old_url; plan_ref; action as above; target_url absolute approved HTTP(S) or null for nonredirect; replacement_reviewed bool/null (only redirect); terminal_statuses nonempty unique list of integer 200–599 excluding supported redirect codes and 304, or null (remove only 404/410). trace object: status complete/partial/failed/not_collected, context_matched bool/null (reviewed method GET, URL, environment/profile/revision, not authenticated by tool), evidence_ref nonempty for attempted or null for not collected, transactions up to 30 each exact absolute url, integer status 200–599, resolved_location absolute reviewed URL or null, evidence_ref. URL checks are limited input hygiene (no credentials, fragment, whitespace/backslash, port zero or bad percent escapes), not standards-complete parsing or network permission. Origin comparison uses parsed scheme/host/effective port only, not DNS, Unicode IDN or real authorization. A non-followable status must have null resolved_location in this projection; retain other raw headers externally. First transaction must equal old URL, next must equal previous reviewed Location. Complete requires non-loop terminal response other than 304 or supported redirect; partial can preserve known prefix even when collection stopped, failed/not_collected have no transactions. Partial prefixes may contain affirmative loop/chain/out-of-scope observations; terminal conclusions deferred. A known unapproved destination can appear as last Location but not a collected request in this projection. Never perform the request. Matched trace allows comparison of first status, complete final URL and status; exact URL comparison may require manual equivalence review. Planned graph flags chains/cycles and planned target removals independently of network evidence. Unknown replacement review flagged for permanent moves. Query preservation tested via reviewed exact desired destination, not automatic query normalization. No raw Location parsing, host-rule evaluation, content equivalence, authorization, DNS or network. All outputs review required; exit zero means processed, not a successful migration. See [synthetic fixture](../../examples/migration/README.md).

## VERIFY
Before cutover review map coverage by cohort, actual target content and status, existing host/rule ordering, rollback and protected staging. Use approved tests for direct GET old URL and every hop, target GET, exact status and complete trace, intended query/locale, HTML/content/directives/canonical/links, new sitemap and critical assets, access boundaries, real UI/forms and analytics (separate authorized method-sensitive tests). Test unmatched paths, old redirect chains, relative Location, Unicode/encoded paths, repeated params, protocol/host variants, missing and temporary error routes. Confirm old origin continues serving redirects, new host capacity and TLS. Compare source/render and actual deployed response separately. Record technical acceptance, then actual authorized processed search evidence and business outcomes separately. A partial crawl cannot prove entire migration complete.

## MEASURE
Compare old/new URL mapped cohorts (including retired and retained), traffic/impressions/clicks and conversions combined where appropriate; annotate change times, seasonality, device, locale, search demand and reporting delay. Track confirmed mapping coverage, wrong target/status, loops/chains, unvisited records, server errors and resource delivery. No invented transfer percentage or guarantee. Verify search processing with T06; do not mark success from live redirects alone or failure from expected short-term fluctuations.

## ADAPT
Hosting-only: preserve user-facing URLs, verify new infrastructure and DNS rollout, monitor both hosts before retirement. SPA: verify actual HTTP and direct entry (T03); Next.js: cache/streaming/host behavior (T04). Multilingual: preserve locale equivalence and RTL/encoding, verify alternate targets, no forced locale alias based solely on strings. Ecommerce: preserve meaningful product/filter/pagination query behavior and attribution. Large site: use reviewed mapping generation and bounded representative checks plus coverage accounting. Limited host access: document actual status limitations; no unapproved workarounds. No search or crawler access: rely on supplied evidence and mark outcomes unknown.

## RECOVER
Before release define stop/rollback criteria and owners using actual business/technical baseline, not universal numbers. Stop for confirmed material wrong redirects, loops, critical route failures, lost protected access or data exposure. Revert smallest approved affected config/release, restore consistent old/new signals and content; avoid oscillating redirects or leaving conflicting versions. Coordinate DNS/CDN/cache and certificate effects; permanent redirects can be cached, so rollback is not instantaneous. If Change of Address submitted, follow approved current cancellation procedure and restore matching redirects/site behavior rather than assume config alone reverses it. Verify both origins again, preserve evidence and annotate processed-state lag. Do not retire old host or evidence because audit timed out.

## EXTERNAL PROVIDER EVIDENCE REQUIREMENTS
Optional WebsiteBotScroll or other approved provider may supply raw discovered/requested/normalized/final URLs, policy version, origin and profile scope, individual HTTP transactions/status, raw and reviewed resolved Location, capture completeness/stop reason/timestamps, target content and directives, canonical/link/sitemap observations and actual resource errors. Preserve meaningful params without exporting sensitive tokens. No inference of equivalence, strategic action, migration approval or search outcome from transport. Project context supplies reviewed old/new mapping and expected behavior. Shared schema pending exact review; no provider-specific adapter, crawler, REST or MCP.
