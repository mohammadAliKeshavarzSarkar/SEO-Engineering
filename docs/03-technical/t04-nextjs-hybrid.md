# T04 — Next.js, SSR, SSG and hybrid architecture

Status: initial implementation methodology and offline route-plan/freshness QA. No actual Next build, runtime, cache invalidation, browser or deployed audit executed. Selected official documentation inspected 2026-11-18. Prerequisites: [T01](t01-architecture-detection.md), [T02](t02-javascript-rendering.md), and [T03](t03-react-vite-spa.md).

## WHAT
Choose and validate route-level delivery, data and metadata ownership in existing Next.js applications. Separate App Router and Pages Router, Server/Client Component boundaries, build-time output, runtime rendering, incremental regeneration, streaming, server/data caches, CDN and client navigation caches. Do not infer generation mode from a Server Component or the presence of HTML. Hybrid means an explicit mixture of delivery or cached/runtime work, not one universal configuration.

## WHY
SEO and user experience can regress when the deployed runtime does not support the selected generation mode, new/deleted paths and sitemap updates disagree, a cache serves obsolete content or metadata, or streaming begins before a missing-resource decision. Preserve useful UI and existing routes. A server-rendered document is not necessarily current, accessible, correct or indexed. Fix the actual owner before changing framework or caching across the app.

## WHEN / WHEN NOT
Use for a verified Next.js route, generation/metadata/cache issue, static-export limitation, new route or deployment regression. Prefer retention when tested behavior already meets the objective. Confirm installed version, actual deployment mode, route ownership and permissions first. Never switch all routes to force-dynamic or cache everything as a blanket SEO fix. Never cache personalized payloads in public output; authentication and authorization remain actual data-access controls. No runtime calls, install/build/deploy, cache purge, revalidation or private tests without appropriate authority.

## INPUTS
Resolved Next/React versions and runtime, next.config, route tree, router ownership, lockfile, builds and host/adapter, selected cache model (including whether Cache Components is enabled), public concrete route registry and locale, purpose/index policy, request-time dependencies, data/metadata owner, freshness objective and known published content revision, mutation/invalidation evidence, actual HTTP source/rendered capture, cache topology, visibility and access evidence. Record which dimensions are unknown. Configuration is a declaration, not observed production behavior.

## HOW

### 1. Detect actual router, version and cache model
Inspect files and configuration as text before executing trusted project commands. App Router commonly uses app segment layouts/pages, metadata exports, RSC and route handlers; Pages Router uses pages and page data functions. Both can coexist; inspect particular route and collisions, not directory presence alone. Verify package lock and deployed version. In newer App Router releases async route params and request APIs require version-appropriate usage. Do not paste latest examples into older projects. Next.js 16 introduced the Cache Components flag, with its own caching model. Legacy segment controls such as dynamic/revalidate/fetchCache are replaced in that mode by explicit cached scopes and cache lifetime controls. Earlier App models and Pages API behavior differ; inspect exact minor release, experimental flags and host support. Do not assume universal fetch caching defaults across releases.

### 2. Choose delivery based on actual route need
| Need | Candidate | Required evidence |
|---|---|---|
| Stable finite published content | Build-time/static | Real parameters, content snapshot, output mapping, refresh process |
| Public content changing within a defined tolerance | Runtime-enabled ISR or appropriate explicit cache/revalidation | Freshness target, successful refresh and deployment support |
| Request-specific public content needing freshness | Request-time rendering or supported hybrid | Actual data latency, failure/status correctness, cache variation |
| Public stable frame plus dynamic regions | Supported hybrid/streamed boundaries | Initial shell, complete response, runtime regions, hydration and host support |
| Protected application | Authorized runtime or safe client shell | Data-level access control and non-public payload handling |
| Removed/unknown route | Correct missing status or approved move | Actual HTTP behavior, content existence, sitemap and links |

App Router Server Components may run at build time or request time. Client Components can still contribute to initial HTML and then hydrate; use small client boundaries for state/browser APIs, preserve motion and interactions. Do not move everything into a client component simply to change metadata. Server-only modules prevent unintended client imports where supported, but do not automatically prevent data serialized in props, HTML/RSC/JSON or logs. Review data projections and access at the source. Pages Router data functions run server-side; serialized props still reach clients.

### 3. Plan concrete dynamic routes
App Router: generateStaticParams enumerates concrete build paths; dynamicParams and route generation depend on cache model/version/deployment. It is not invoked again during ISR. With current Cache Components, a supplied generateStaticParams must return at least one param; do not blindly apply an empty-array pattern from previous ISR tutorials. Avoid fabricated placeholder routes as default. For compatible Cache Components routes without generateStaticParams, unknown params are runtime data and access needs the documented Suspense handling; supplying representative build-time params instead exercises only the code paths reached by those samples. Validate remaining runtime branches and never claim blanket coverage from a passing build. See [dynamic segments](https://nextjs.org/docs/app/api-reference/file-conventions/dynamic-routes) and [empty params guidance](https://nextjs.org/docs/messages/empty-generate-static-params). Pages Router: getStaticPaths with getStaticProps; fallback false builds enumerated paths and other paths are missing; true/blocking require compatible runtime and have different initial behavior. getServerSideProps is request-time, not combined with getStaticPaths/getStaticProps on that page. Preserve actual published Unicode/localized path values from registry; distinguish unpublished, removed and temporary data errors. New slugs, deletion and redirect behavior need explicit entry tests.

### 4. Match deployment to runtime requirements
Static export (output: 'export' in compatible versions) means build-generated output served by host, not a Next rendering server. Request-time APIs, ISR, server actions, request-dependent handlers, framework runtime redirects/rewrites, Pages API routes and default image optimization may require runtime support and are incompatible with ordinary static export as applicable. Static GET handler output and custom image loading may work under documented restrictions; host-native redirects/headers can be supported independently. Do not generalize that every host cannot redirect. Review actual unsupported-feature lists for chosen router/version. Distinguish Next output/trailing slash/basePath, asset URL, CDN, reverse proxy, runtime/adapter capabilities. Use T03 artifact-plan check for intentionally static files with explicit mapping; do not require one local HTML file for a legitimate runtime route. Verify `next build` output, authorized production-like runtime and actual host responses separately. Development mode does not prove production cache behavior.

### 5. Establish metadata and primary-content ownership
App Router: use static metadata or generateMetadata in compatible server layouts/pages (not both in the same segment), metadataBase from trusted reviewed origin, route-specific alternate/canonical/open graph decisions, and file-based metadata where applicable. Inspect layout inheritance, merge/replacement behavior and file precedence; avoid a homepage canonical inherited by every distinct page. Pages Router: inspect next/head and actual page declarations, not App Router exports. Use a single reviewed public content source for page content, canonical, locale alternates, share metadata and sitemap entries; ensure exact status and intended indexing. Metadata generation should share the authoritative published record, not fabricate values or expose credentials. Keep JSON-LD consistent with visible facts and safely serialized. Validate output and no conflicting initial directives; use T02 for source/render and T08 when available for detailed structured data.

Next may stream metadata after the initial UI for supported dynamic rendering; for some HTML-limited clients framework waits for metadata. Full completed response and ready browser DOM are different observations from an early stream prefix. Do not label documented streamed metadata automatically invalid just because it is outside the early head; inspect actual supported behavior, crawler applicability and full response. T02 and static checker explicit-head conventions must not be applied as universal rules to a partial or streamed capture. No user-agent cloaking workarounds. Validate share preview and authorized platform inspection separately.

### 6. Design freshness and invalidation by data owner
Define an explicit business freshness objective (e.g. a published content revision visible to aligned public requests by a reviewed deadline). Time-based revalidation is not a timer guaranteeing all future requests new content at that second. ISR may serve an existing response while work refreshes asynchronously; upstream errors may retain earlier successful output. Distinguish known deleted content from failed fetch. Record first request after expiry, later request, actual revision marker from rendered content/metadata, and error evidence. No destructive live cache purge merely to test. A change in cache header or response time is not proof of correct content version.

Map caches: upstream data/CMS; server data and generated response; host/CDN and proxy variants; client router/prefetch/browser caches. Inspect each applicable layer, key dimensions (locale, content/tenant, relevant query, authorization and representation), tag/path relationships, invalidation propagation, actual deployment version and cross-instance coordination. Never put authenticated data into public cache or coalesce tenants. For App previous model use documented fetch cache/revalidate settings, route segment config and relevant tag/path invalidation APIs for that version. For Cache Components use explicit use cache scopes, cacheLife/cacheTag and documented revalidation semantics; updateTag is a different intended operation from stale-while-revalidate semantics, verify support/call context. Do not mix controls blindly. Pages Router use getStaticProps revalidate or documented authorized on-demand revalidation. On self-hosted multi-instance deployments, verify shared cache/invalidation coordination, CDN Vary/cache keys, build compatibility and error behavior; one node reporting new content does not establish global consistency. Preserve auth, rate limiting and integrity of existing mutation endpoints. Never expose unrestricted invalidation APIs; authenticated, validated allowed path/tag, bounded authorized action and audit required.

### 7. Handle status, streaming and failures
Resolve existence/access before response commits when accurate status is critical and supported; inspect notFound(), redirect and loading/Suspense boundaries from actual version. App streaming can send HTTP 200 before a later not-found/redirect state; headers cannot then change. Treat useful error UI, robots evidence, final response status and search-selected soft-404 as distinct. Test nonexistent direct route; do not claim notFound always yields HTTP 404. Prefer architecture that delivers actual intended status when feasible without breaking useful UX. Pages data functions support notFound/redirect results in applicable contexts. Temporary backend failure must not be translated to permanent disappearance, unrelated redirect or a durable cached empty page. Preserve source evidence for review and existing rollback.

### 8. Offline route-plan and freshness QA
Use scripts/audit_next_delivery.py on a reviewed local projection (NOT the external evidence schema). Input: schema_version "1", scope, routes (1–500). Each row: id, plan_ref, next_major (integer 1–100/null), router app/pages/unknown, cache_model app_previous/app_cache_components/pages/unknown, deployment static_export/runtime/unknown, strategy static/isr/request_time/hybrid/unknown, purpose public/excluded/protected/missing/redirect, expected_context (opaque reviewed context ID), required_features (unique known feature strings or null), expected_statuses (nonempty unique HTTP integers or null), expected_content_revision (nonempty string or null), fresh_by (UTC timestamp or null; both target and deadline specified together), samples (0–100). Feature enum: request_time_data, isr, runtime_dynamic_paths, server_actions, request_dependent_handler, next_runtime_redirects_or_rewrites, pages_api_routes, default_image_optimizer. These are reviewed requirements, not automatically detected. Samples: globally unique id, context_id, capture_status complete/partial/failed/not_collected, evidence_ref and observed_at (attempted capture reference and UTC YYYY-MM-DDTHH:MM:SSZ, both null if not collected), http_status integer/null, content_revision nonempty string/null, private_payload_visible boolean/null (reviewed unauthorized visibility, never inferred from noindex or cache). Failed/uncollected have null observed values. For complete matching context, status compared against reviewed expectation; exact content revision matched only where 200 and target present; different content before deadline informational, at/after deadline review, not necessarily older content or cache fault. Choose a tested revision marker and target that remains relevant to that sample window; different newer revision also needs manual review. Missing/partial/mismatched samples defer comparisons; affirmative unauthorized payload exposure flagged independently. No false security assurance from false/unknown. Static export feature conflicts and cache model/router/major inconsistencies are review findings. Unknown plan inputs remain unknown. Context includes reviewed route, deployment, representation, audience, locale and variant; sample method/instance tracked separately in evidence. Label reflects supplied comparability, not verified by utility. No cache reads or writes, network or build; success means processed, all results require review.

## VERIFY
Run chosen route contract for build/runtime/host and source/render separately with authorized tools. Test a finite known path, new dynamic path, missing/removed path, redirect, protected route, locale and required public links. Compare actual headers/status, initial/full streamed metadata and readiness DOM, client navigation, assets/RSC or JSON data, content revision and share state. For a safe synthetic freshness test publish a known revision in isolated environment with agreed deadline, sample representative instances/profiles at recorded times, record earlier/later results and errors, verify no cross-user/locale leakage and rollback/invalidation path. Do not perform mutations just to collect SEO evidence without approval. Review sitemap/robots and authorized processed search status separately. Reuse T01/T02/T03 and [Next patterns](../../implementation-patterns/nextjs-delivery.md). E51–E54 are public behavioral scenarios, not measured model outcomes.

## MEASURE
Track aligned route coverage, intended vs observed status, revision-target observations within defined windows, mismatch/deferred counts, error and recovery patterns, cache scope/instance differences and real UX/performance. Report denominator and time/deployment variant; no inference of global freshness from one hit. Measure search/traffic and conversions separately with authorized data.

## ADAPT
Static export: enumerate all needed concrete paths and host limitations. Pages Router: use existing supported data functions, no automatic migration. App previous versus Cache Components: inspect version and docs, keep current model unless change justified. Hybrid/streaming: capture completed body and readiness, distinguish status commit timing. International: retain locale-specific data keys, canonical, alternates and RTL, no accidental variant merge. Large catalogs: choose bounded representative request/refresh cohorts and public generation registry. Missing code/runtime access: report evidence gaps; do not assert actual mode/caching. Preserve accessible UI and existing interaction boundaries.

## RECOVER
On private payload exposure stop rollout and escalate, preserve sanitized evidence, revoke or invalidate affected caches/credentials only through approved incident response; do not merely add noindex. On incorrect status, content or metadata, isolate route/data owner, upstream failure, cache scope and deployment mismatch. Stop unsafe release and revert smallest approved change, verify again under matched conditions. Cache or version migration needs coordinated rollback; do not globally purge unrelated content or silently reuse old evidence.

## EXTERNAL PROVIDER EVIDENCE REQUIREMENTS
Optional authorized provider may collect requested/final URL, redirect and HTTP status, repeated relevant headers (Cache-Control, Age, Vary, ETag, Last-Modified, X-Robots-Tag and observed framework/host cache diagnostics), source/full-stream/DOM capture status, content revision marker when explicitly defined, source/render metadata, timestamps, request profile and evidence references. Record if intermediate or incomplete. Cache headers are observations, not authoritative internal configuration or correctness. Project owner provides version/config, topology, known content target, deadline, cache policies and authorized mutation evidence; a crawler is not an invalidation tool. Do not require access to private or signed URLs or export secrets. Shared WebsiteBotScroll schema is pending exact review; no field mapping, provider adapter, REST/MCP or new crawler added.
