# T03 — React, Vite and SPA SEO engineering

Status: initial implementation methodology and local artifact-plan checker; actual framework builds, deployed acceptance and independent behavioral evaluation pending. Sources checked 2026-11-18. Prerequisites: [T01 architecture detection](t01-architecture-detection.md), [T02 rendering engineering](t02-javascript-rendering.md).

## WHAT
Improve public search acquisition delivery in React/Vite applications without unnecessarily replacing the interactive frontend. Separate router mode, bundler, generation strategy, hosting and the actual HTTP response per concrete URL. A client-side route is not necessarily a unique build document; a static HTML file is not necessarily served for that URL. Existing useful React components, animation, navigation, accessibility and protected application functionality should survive a repair.

## WHY
An SPA can work when navigating from home but fail on direct links, or a global fallback can return a successful shell for nonexistent routes, APIs and missing assets. Metadata may be controlled independently by HTML templates, layouts and components. A prerender build can omit dynamic article/locale paths or be deployed under the wrong public base. Fix these distinct owners with evidence. A framework migration, generated files or a title update alone cannot establish search indexing.

## WHEN / WHEN NOT
Use for React applications with Vite or other bundling, browser routing, client-only public content, static builds or route-level prerendering. Verify installed versions and actual mode first; React Router Framework Mode configuration is not a feature of every BrowserRouter/Vite project. When source/render/status behavior already meets the route contract, retain it. Never prerender sensitive user data, infer authorization from robots or publish private routes for search. Do not execute project scripts/install dependencies, change router or hosting, or deploy without appropriate authorization.

## INPUTS
Target app root, manifest and resolved lockfile, actual build scripts/config and route definitions, router mode, public base and router basename, build output paths, reviewed concrete URL/content inventory and locale/parameter policy, intended access/status/canonical/sitemap, source/head owners, hosting/edge routing and runtime support, approved build and request evidence. Separate declared intent from actual artifacts and deployment behavior. Keep private project evidence outside the universal library.

## HOW

### 1. Recognize the existing implementation
Inspect package.json, lockfile, entry HTML, React client/server entrypoints, route table, data loaders and metadata mechanism, Vite build config (including base/outDir), public assets, host routing config and build logs as text first. Verify framework versions or current version-specific documentation before using APIs. A Vite production build generally bundles a client app; an SSR setup, multi-page input or framework integration can produce other output. React Router has declarative, data and framework modes; a client router on its own does not automatically generate a document or server request handler for every route. Use T01 evidence and do not assume a deployment matches the checked-out code.

### 2. Select the smallest architecture for each route
| Route need | Candidate (not automatic) | Verify |
|---|---|---|
| Existing public route works in source and render | Retain architecture | Status, declarations, content, links, UX and deployed parity |
| Existing CSR public route has reliable completion | Retain/repair CSR | Direct entry, resource and data reliability, processed evidence if available |
| Finite stable public article/service/locale routes | Build-time rendering or static entries | Concrete paths, data availability, public-only payload, refresh and host mapping |
| Dynamic public data/freshness requirement | SSR or supported hybrid | Runtime hosting, status, cache, latency, failure and data ownership |
| Protected interactive application | Existing authenticated app, often client shell | Real authorization and no private payload in public artifacts |
| Unknown/moved/invalid paths | Accurate host/server handling | Status/Location, error UX, no generic success or home redirect |

Use existing router/framework capability before introducing another dependency. For static deployments, enumerate actual published dynamic URLs from a reviewed content registry, not just route patterns such as /blog/:slug. A hash route is client-only state, not equivalent to an independent server path; preserve supported legacy links and plan any URL migration separately (T07). Do not migrate useful URLs to new slugs just to make output easier.

### 3. Build a reviewed route registry
Use stable page IDs, concrete canonical URLs, purpose (acquisition/public utility/protected/missing/redirect), locale, declared delivery, expected status/redirect, content ID, data freshness, intended sitemap membership, metadata and actual generation/hosting owner. Generate or reconcile build routes, canonical preferences, navigation and sitemap intent from a shared authoritative registry where appropriate. Not every router path should be an indexable destination. Keep planned destinations, observed links and canonical selection separate. Validate route collisions and preserve meaningful query parameters and percent encoding; don't normalize URLs into filesystem names automatically. Resolve public base, router basename and host URL-to-file rules separately. Vite base governs built asset references, not by itself the router's URL matching or canonical origin.

### 4. Implement metadata without competing owners
Use the already supported head/route metadata mechanism. React 19 supports document metadata components, but older React releases and other head libraries have different behavior. Render a single appropriate document title and intended canonical; distinguish SVG title, nested routes and root defaults. In a client-only app, client metadata still depends on rendering; it does not retroactively change the HTTP response. Avoid initial homepage canonical on every path and unintended initial noindex. Where initial route-specific canonical is not available, a single consistent JS-added declaration without a conflicting source declaration is an option; verify behavior and preferences. CSR effect-based head updates must handle direct entry, async failures, route transitions and cleanup, not leave stale tags or multiple canonicals. Prefer initial route-specific useful content and head when chosen generation supports them. Escape data via framework facilities; no untrusted innerHTML or arbitrary request Host to canonical construction. No fabricated claims, schema or locale metadata.

### 5. Deploy static, SPA and hybrid paths deliberately
Read actual host documentation/version and existing routing precedence. A suggested order to adapt is authorized API/protected routes and actions, explicit redirects, existing correctly mapped static documents/resources, a restricted SPA fallback for known app routes as appropriate, then genuine not-found handling. Actual order depends on host and app; check security and don't blindly implement it. Never rewrite missing JS/data or API errors to HTML. Request static assets and client navigation data independently; a 200 HTML response for a missing JS chunk is a failure. Host behavior for slash variants, nested base, URL decoding, default index documents, query preservation and error documents varies. Verify per-route 200/redirect/404/410/access responses on deployed or representative authorized staging host; a client error component cannot change the already returned HTTP status.

For static-only hosts with unrestricted successful fallback and no per-route status control, document limitations. Google describes two SPA not-found alternatives: navigate to a URL that actually returns 404 or add noindex on the actual rendered error page. Prefer genuine status where feasible. These alternatives do not turn the original response into HTTP 404, and a JS noindex must not be added to useful valid routes or assumed processed; distinguish known missing resource from transient failure or intentionally empty result. Keep the error UI useful. No crawler-only content workaround as default.

### 6. Validate actual build artifacts
After authorized, reviewed build execution, record revision, runtime, exact output directory and generated paths. Use the explicit local plan helper scripts/audit_spa_build.py. It does not run a build, parse host rules, interpret bundler manifests, resolve assets automatically or assert actual delivery. See [synthetic fixture](../../examples/spa-build/README.md). Inputs: schema_version "1", scope string, routes (1–2000): id, absolute HTTP(S) url, purpose (acquisition/public_utility/protected/missing/redirect), delivery (prerendered/spa_shell/runtime/none/error_document), boolean sitemap_expected, canonical_expected (absolute URL/null), html_file (explicit relative path for prerendered/spa_shell/error_document, null for runtime/none), required_files (up to 100 explicit relative paths). JSON parser rejects duplicate keys/non-finite numbers. Paths use forward slashes, no absolute/hidden/traversal/colon/backslash components, and no symlinked path components within the explicitly selected trusted root. Regular nonempty file checks only; no file content read. Do not run against a concurrently mutated or untrusted filesystem; root explicitly trusted, not a sandbox. No automatic URL-to-path guessing. Exact strings identify URLs, ASCII/Unicode spelling retained; case-folded path collisions are conservative portability warnings, not filesystem equivalence guarantees.

Flags include missing/empty/nonregular required artifacts, conflicting document path mappings (shared shell or error document intentionally allowed), reviewed protected prerender plan risk, non-acquisition sitemap plan, non-self canonical sitemap plan review, bad acquisition/redirect document plan and missing-path shell status risk. Unknown expected canonical remains deferred. These are project-plan checks, not universal rules. Use existing scripts/audit_html.py against actual local indexable HTML where applicable to check its narrow source convention; do not apply its exact-one metadata/H1 convention to every shell or runtime route. Use T02 for matched source/render observations. A successful CLI exit means processed, not a passed build or release.

### 7. Build and browser acceptance
Run approved existing project quality and build commands with pinned runtime/dependencies, after inspecting scripts and environment requirements. Use actual build output, not dev server only. Vite preview is for local preview, not production server. Check production-like host/staging separately and record differences; do not expose local preview unnecessarily. Test direct and cold entry, client navigation, reload on nested paths, back/forward, modified clicks, locale/mobile and interactive state. Inspect missing assets and data, source and rendered title/canonical/directives, primary content, links, deployment revision and caches. Validate that expected fallback applies only where intended. For a static generation change test all bounded planned paths in build and representative live paths, including dynamic slugs missing from build, removed/renamed slugs, and source/render parity. Sample actual performance and maintain animations, focus, scroll and accessibility. Verify no protected data in build outputs or logs, and access controls through separately authorized synthetic tests. See [React/Vite patterns](../../implementation-patterns/react-vite-spa.md), [SPA decisions](../../decision-engine/spa-delivery.md), [route delivery](../../implementation-patterns/route-delivery.md).

## VERIFY
Record concrete route IDs, expected and observed delivery/status, manifest/build paths, direct response evidence and exact deployment revision. Check distinct route-specific documents where selected, resources/data, initial metadata and applicable headers, no interactions baseline, meaningful browser readiness, actual URL/link behavior, protected/excluded routes and missing/error/redirect routes. Do not infer deployed mapping from file existence; compare host and user experience. Use actual authorized Search Console evidence for search-specific outcomes; local validation is not indexing proof. Behavioral cases E47–E50 are proposed public development scenarios.

## MEASURE
Track build-plan coverage (planned vs present per route class), route-specific HTTP/metadata/content parity, failed chunks/data, missing-route status, release regression count and actual UX/performance guardrails. Distinguish skipped/unknown/runtime-only records. Compare matched routes and versions before/after; search visibility and conversions separate. No universal target for JS amount or number of prerendered pages.

## ADAPT
Plain React/Vite client app: retain router, consider explicit static entries or supported prerender integration only if justified. React Router Framework Mode: inspect version, static/dynamic path enumeration, generated client/data files and host/runtime contract. Custom Vite SSR: inspect existing server entry and adapter; next module covers separate Next.js ecosystem, not a mandatory migration. Multilingual: preserve source language and URL encoding, route variants, direction and actual hreflang. Large site: bounded sample and complete build registry where feasible; don't prerender unlimited combinations. No code/build access: review actual public observations and report implementation unknowns. No hosting control: explain status limitations and options. No browser/provider: defer rendered claims. All changes require scope and authorization.

## RECOVER
If build omits paths, verify content enumeration and actual output before deployment; stop on private data or critical route regression. If static host falls back incorrectly or assets break, inspect path and routing precedence, base settings, stale CDN/build versions and correct affected layer. If initial content/metadata regresses, revert affected build/configuration under approved rollback; retain URLs and interactive state. Record matched verification and remaining uncertainties. Do not silently mark a partial build complete or overwrite source evidence.

## OUTPUTS
[SPA route-build inventory](../../templates/spa-route-build-plan.csv), [local plan exercise](../../examples/spa-build/README.md), source/render and deployed evidence, owner/decision record, smallest authorized implementation and acceptance/rollback. No actual framework build or target deployment performed in this module.

## EXTERNAL PROVIDER EVIDENCE REQUIREMENTS
An optional evidence provider such as WebsiteBotScroll could collect authorized concrete requested/final URL and status/redirect hops; content type and repeated HTTP directives; initial/rendered metadata with provenance and completeness; asset/data response and network failure evidence; real anchors, render readiness and interaction state; scope/coverage and version. An observed HTML response for an asset request should be recorded, not assumed successful JS. Deployment configuration, expected build paths, router mode, dynamic slug inventory, strategic sitemap/canonical intent and authorization requirements require separately reviewed project inputs. No provider may infer deployed architecture from one HTML document. Shared 0.1.0 contract pending exact review; no external schema mapping, crawler, API or MCP added.
