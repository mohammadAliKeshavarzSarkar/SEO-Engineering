# T09 — Core Web Vitals and performance engineering

Status: initial methodology, implementation patterns and offline field/lab evidence QA. No real site measurements, browser traces, runtime instrumentation or deployed optimization executed. Selected primary sources reviewed 2026-11-18. Use [T01](t01-architecture-detection.md), [T02](t02-javascript-rendering.md), [T03](t03-react-vite-spa.md) and [T04](t04-nextjs-hybrid.md) for delivery context.

## WHAT
Improve actual loading, responsiveness, visual stability and task completion while preserving valuable content, accessibility, interactive state, brand motion and visual quality. Distinguish field distributions, controlled laboratory measurements, per-interaction attribution, resource budgets and search outcomes. Core Web Vitals (CWV) are not a single synthetic score.

## WHY
Slow primary content, delayed interaction feedback and unexpected layout shifts harm real users. Optimizing a lab score without understanding field bottlenecks can shift cost to another stage, hide content, delay essential interaction or remove valuable features. Diagnose the actual bottleneck and choose the smallest justified change.

## WHEN / WHEN NOT
Apply when field evidence indicates material performance issues, a reproducible journey is slow, a release changes assets/rendering/dependencies, or an agreed budget regresses. Retain verified healthy implementation; Lighthouse 100 is not an objective by itself. Never remove primary content, accessibility controls, consent, authentication or useful animations solely to improve a score. No unapproved testing, tracking installation, external APIs, production build/deployment, cache mutation or high-load collection. Browser runs require authorized targets, restricted isolated environment and bounded requests including subresources.

## INPUTS
Reviewed route/template and business journey, design/interaction/accessibility acceptance, exact deployment and build revision, URL/origin or explicit group, device and field provider, aggregation window and method, metric and unit, sample coverage if available, lab tool/browser/version and settings, network/CPU/viewport/cache state, locale and auth profile, navigation or interaction steps, resource/trace evidence and actual errors, before/after release hypothesis, pre-agreed tolerances, review and rollback owner. Missing observations remain unknown. Keep private traces and user-derived data under approved privacy policy.

## HOW

### 1. Separate measurement types
| Metric | Meaning | Good field p75 | Poor field p75 |
|---|---|---:|---:|
| LCP (ms) | Largest Contentful Paint | <=2500 | >4000 |
| INP (ms) | Interaction to Next Paint | <=200 | >500 |
| CLS (unitless) | Cumulative Layout Shift | <=0.1 | >0.25 |

Values between thresholds need improvement. These recommended field categories apply to 75th percentile observations segmented by device. They are not mandatory lab budgets or universal release thresholds. FCP, TTFB and TBT are supporting diagnostics, not Core Web Vitals. Lighthouse navigation TBT measures main-thread blocking during lab load; it is not field INP. Lab interaction latency from a specified event is useful for reproduction but does not establish a full visit's INP. Missing INP can reflect no qualifying interactions or insufficient observations; never substitute zero or TBT.

CrUX covers eligible real Chrome experiences, not all users. PSI reports trailing 28-day field observations and a separate Lighthouse lab run, with URL-level versus origin-level scope. Origin fallback is not page evidence. Record actual reported subject, device, date window, source and metric values; do not mix a URL and origin or average percentiles across pages/devices. Google Search Console CWV groups similar URLs and tracks field evidence; review actual group, not a full census. Know provider-specific aggregation: PSI may assess an aggregate without INP if both available LCP and CLS are good; our conservative offline summary requires all three present. Never relabel it as PSI pass. No data means unknown, not healthy. Do not infer exact visitor counts from CrUX. Query variations may be aggregated under provider methodology; preserve project identities separately. Field windows can overlap releases; no immediate post-release verdict or causal proof from a moving aggregate.

For approved RUM, use existing supported measurement library (e.g. web-vitals with installed-version API review), vital finalization/lifecycle handling, explicit route attribution, sampling and consent as applicable. Keep bfcache, long sessions, SPA navigation and interaction measurement semantics clear. Do not treat a client route change as a fresh standard navigation CWV sample by default. Avoid collecting raw DOM text, typed inputs, personal IDs, signed URLs or sensitive query strings; use reviewed coarse route IDs and aggregate metrics with appropriate retention and access controls. No full-session recording by default.

### 2. Establish reproducible baseline
Select representative public acquisition pages and real user journeys (navigation, menu, filtering, form control, responsive transitions). Preserve design acceptance and content equivalence, including locale, correct media, keyboard/focus, reduced motion and error/empty states. Separate cold/warm cache and real-device versus emulated/throttled runs. Record actual tool/version, browser, settings including throttling method, viewport, network/CPU, location if relevant, cache and service worker state, interaction sequence and build. Do not compare Lighthouse scores from different versions/settings as though identical. For field review compare aligned source, device, route/aggregation and windows; distinct traffic compositions and overlapping windows constrain inference. For lab comparisons predeclare metric, repetitions, order/counterbalance and tolerance; repeat under fixed profile, retain failures and spread (median/range as descriptive summaries, not significance). Measure actual resource bytes (transfer versus decoded), requests, long tasks and trace attribution where available. No arbitrary universal KB, request count or animation FPS gate.

### 3. Diagnose LCP by subpart
Identify actual LCP element for each relevant viewport/profile. It may be text, image or video poster, not necessarily the hero asset. When resource attribution is available, split LCP into TTFB, resource discovery/load delay, resource load duration and element render delay. Inspect waterfall and main-thread timeline; compare actual timings rather than enforce fixed subpart percentages. Need no resource for text rendered with system font in some cases. Optimization in one phase may only move delay to another.

- TTFB: investigate redirects, connection, origin processing, cache miss and upstream requests; use measured server timing and T04 freshness policy where relevant. Do not cache personalized data publicly.
- Discovery delay: make actual critical resource discoverable early through initial markup or correctly scoped preload when necessary. Do not lazy-load known LCP image; use deliberate fetch priority on selected resource, not all assets. Dynamic CSS backgrounds and JS-inserted images may need different handling. Avoid duplicate downloads via mismatched preload and responsive candidates.
- Download: use appropriately sized responsive image variants and formats (such as WebP/AVIF where supported), compression by visual quality, CDN/cache where justified. Preserve intrinsic dimensions, useful alt and actual content.
- Render delay: inspect blocking CSS, fonts, JS evaluation/hydration, hidden loading shell or entrance animation. Do not hide primary content until every optional animation/library completes. Keep meaningful entrance motion for nonessential decoration or compositor-friendly transitions while primary content is visible. Evaluate actual render/UX and avoid blanket SSR migration.

### 4. Diagnose INP by interaction
Use field attribution where available to identify slow real interactions; reproduce approved representative click/tap/key paths, including early startup and long-session states. Separate input delay (work queued before handler), processing duration (callbacks), presentation delay (rendering/layout/paint). Inspect relevant frame and main-thread tasks. Reduce long tasks by splitting and yielding where safe; move suitable CPU work into workers only after messaging/serialization and correctness review. Use smaller route bundles and targeted component boundaries, defer optional work and third-party scripts without breaking consent or critical behavior. Avoid frequent layout read/write interleaving, excessive DOM commits, heavy synchronous SVG/chart calculations and event bursts. Immediate meaningful feedback may precede noncritical work; preserve actual task completion, correctness, focus, form and navigation behavior. Debounce/throttle only appropriate nonessential frequency, never lose user intent or introduce hidden latency. Test actual interaction and next paint; lab TBT improvement alone is not field INP improvement.

### 5. Diagnose CLS across the visit
Inspect actual shifting elements and cause; culprit may be an earlier inserted element. Reserve dimensions/aspect ratios for images, video, embeds, skeletons and dynamic UI near viewport. Use responsive CSS and real content dimensions, not fixed heights clipping translations. Check font swapping and fallback metrics, especially Persian shaping, numerals and RTL wrapping. Use appropriate licensed WOFF2/subsets only if shaping and glyph coverage preserved; choose font-display and targeted preload based on actual trace, not all fonts. Avoid surprising layout changes from banners or data loading; preserve consent and focus/access. Lab initial-load CLS may miss post-load shifts, so test scrolling, route transitions, late updates and long sessions. CLS uses a session-window approach rather than simple lifetime sum; preserve provider metric definitions, don't calculate it from arbitrary screenshot movement.

### 6. Preserve motion and premium UI
Profile actual animation bottleneck, main-thread work, layout/paint, layer count and dropped frames (device/refresh-rate dependent). Prefer transform and opacity where suitable, not guarantees of compositor-only behavior. Reserve layout and use visual transforms for movement where appropriate; test actual hit targets, clipping, stacking, focus and reading order. Use will-change sparingly after profiling, remove when no longer needed. Batch state updates, isolate animation state from large data trees, use supported animation/transition APIs, stop offscreen or inactive nonessential loops as appropriate. Never impose universal removal of SVG, canvas, motion libraries or rich images. Respect prefers-reduced-motion and provide appropriate reduced or static alternatives; preserve informative progress and controls. Verify real low-end mobile behavior, keyboard, contrast, focus, mobile content parity and journey completion. See [patterns](../../implementation-patterns/performance-optimization.md).

### 7. Offline review of supplied performance evidence
Use scripts/audit_performance.py, a local projection, not the shared provider schema. Envelope schema_version "1", scope, field and lab arrays (at most 500 each, nonempty total). Field record: unique id, source crux/rum/other, level url/origin/route_group, subject, device mobile/desktop/tablet/all/unknown, start/end ISO calendar dates, method, evidence_ref, p75 object exactly lcp_ms, inp_ms, cls (finite nonnegative number or null). The operator establishes actual p75 method and scope; tool does not derive percentiles or verify provider. Field values classified independently with stated thresholds; local summary incomplete if any metric unknown, otherwise all_three_good/not_all_good. No URL-origin substitution, cross-window comparisons or rollups. Preserve separate provider assessment externally.

Lab record: unique id, metric lcp_ms/cls/tbt_ms/ttfb_ms/interaction_ms/transfer_bytes, expected_profile (reviewed opaque label including tool/version, route, journey, device, cache, settings and relevant contextual equivalence), baseline_revision and candidate_revision distinct, minimum_runs integer 3–30, allowed_regression finite nonnegative absolute tolerance in metric's units, baseline and candidate arrays at most 30 runs each. Each run id unique within comparison, profile, revision, status complete/partial/failed/not_collected, value number only if complete else null, evidence_ref required unless not_collected. Lower is better for these metrics. Compare equal planned cohort sizes only when all runs complete and aligned and minimum achieved; otherwise defer verdict (descriptive values from comparable subset still shown). Median and range reported per arm, candidate-minus-baseline median compared to predeclared absolute tolerance; within_reviewed_tolerance is not a performance pass, an improvement significance claim or a proof of UX equivalence. Failed runs must not be silently dropped; predefine retry policy externally and preserve original evidence. Output includes evidence refs and limits. No collection, timing API, external request, build, RUM aggregation or rank prediction. New output path; exit zero means processed. [Synthetic exercise](../../examples/performance/README.md).

## VERIFY
Record actual baseline and candidate under aligned settings, trace evidence and meaningful content/visual/functionality equivalence. Exercise initial and late load, cold/warm navigation, actual slow interaction, locale/font fallback, mobile interaction and reduced-motion preference; confirm no resource, status, index directive, consent, access or analytics regression. For approved staging test representative devices; actual deployment evidence separate. Verify field evidence as available over relevant post-release window, not lab proof. Require owner-defined functional/accessibility acceptance before recommending release. E71–E74 are public evaluation scenarios not behavioral results.

## MEASURE
Preserve field per-metric distributions/p75, source/aggregation/device and window; lab median/range, complete/planned counts and metric-specific budgets; diagnostic timings, resource transfer and responsiveness/UX checks. Track journey completion and business outcomes separately with consent and comparable cohorts. Avoid replacing data with composite scores, claiming causality from one run or ranking guarantee. Good CWV is recommended for users and used by Google's systems, not sufficient for ranking.

## ADAPT
Small/static: optimize actual image/font and initial delivery first if indicated. SPA: route bundles, hydration and interaction profiling, do not equate SPA transition metrics with navigation CWV. Next: cache model and deployment per T04, evaluate both TTFB and render delay. Long-lived dashboards: measure actual sustained interaction/animation and memory, not just first load. International: preserve glyphs, shaping, RTL, locale-specific payload and layout. Low field traffic: use approved representative lab and user feedback, field unknown. No browser: supplied trace/report evidence only, no invented scores. No consent to RUM: no instrumentation, use permitted aggregate sources.

## RECOVER
Stop rollout for significant verified regressions beyond agreed tolerances, loss of primary content, functionality/accessibility, or security/privacy exposure. Isolate actual changed assets/rendering/handler/cache owner, revert smallest approved change, verify in same profiles and keep evidence. Do not purge unrelated caches, disable all motion or remove third-party consent arbitrarily. Recheck field after appropriate window, keep lab and actual UX acceptance separate. If evidence mismatched, collect comparable evidence only with authorization. No guarantee of field recovery or search timeline.

## EXTERNAL PROVIDER EVIDENCE REQUIREMENTS
An optional approved WebsiteBotScroll provider may eventually supply typed timed navigation or Lighthouse observations with tool/browser/version, URL and final URL, profile/settings, metric/unit, collection state, raw trace reference, resource entries/transfer vs decoded sizes, relevant timing breakdown and failure/coverage. HTTP fetch timing is not browser LCP; a crawler or Lighthouse navigation cannot manufacture field INP. Real-user aggregate source, window, device, URL/origin/group scope and method are separate observations, not inferred from synthetic runs. Project owner supplies intended journeys, acceptance, release context and privacy decisions. Shared contract pending exact review; no adapter, network collector, RUM installation, REST or MCP added.
