# T10 — Technical audit automation

Status: initial coordination methodology and executable offline runner for the nine existing technical modules. No live crawl, search API, browser, deployment, automated remediation or independent behavioral evaluation. The runner is not the future WebsiteBotScroll adapter. Internal architecture checkpoint 2026-11-18; inputs and outputs reviewed against T01–T09 and R08.

## WHAT
Turn a set of independently useful technical utilities into a traceable, reproducible audit workflow. Select appropriate diagnostics, supply reviewed projections, run existing deterministic checks, keep native results and collection gaps, group related review candidates with evidence, and reuse the strategic prioritization method. Distinguish audit processing, observed discrepancy, confirmed issue, implementation approval and verification. Never replace a technical audit with a single health score.

## WHY
An isolated script sees only its own supplied evidence and policy. A blocked guide can trigger several checks, but this is not necessarily several independent defects. Different crawl profiles, environments and revisions can produce contradictory observations. Unvisited routes, failed tools and local build success cannot establish whole-site behavior or actual search processing. Coordinating provenance, reviewed scope and uncertainties is more reliable than counting warnings or applying all suggestions.

## WHEN / WHEN NOT
Use after setting authority, target scope and goals for a new audit, redesign review, technical baseline or repeatable investigation. Choose only relevant modules; a targeted question does not require running all nine. If evidence absent, defer or block that module. No-change valid. No arbitrary command execution, target project discovery or script execution, crawler, external requests, remediation, publication or release approval here. The trusted library and operator-selected artifact root are not a sandbox. Never read private or unrelated project files.

## INPUTS
Approved scope, reviewed project registry/intent, environment/revision and evidence collection context, route identities and explicit expected behaviors, module-specific local input envelopes (T01–T09), reference to underlying evidence, collection limitations and actual capability. Each input retains its own scope and schema. A run manifest records selection and reason, not proof that source references resolve or that observations align. For grouping: evidence, explicit root-cause/scope rationale, reviewer, owner, acceptance and next check, severity/fit/risk/confidence and optional reviewed impact/effort/dependencies per R08. Preserve sanitized evidence outside universal library. Do not infer context from matching local IDs.

## HOW

### 1. Define scope and evidence plan
Start with read-only authorization, current project and historical baseline, exact origin/environment/locale and intended route registry, business priority and actual tools. Identify the smallest representative cohorts and edge cases. List each module as ready, blocked or not_applicable with reason. Ready means suitable reviewed input prepared, not confirmed diagnosis. Preserve observed/partial/unknown and failed collection inside each module projection, not invented defaults. Record collection time, profile, provenance, actual coverage and stop reason in underlying evidence. A module not selected is not a passing check. Use [execution contract](../../templates/agent-run-record.md) record for owner and run context.

### 2. Select independent modules in a sensible review order
| Module | Review purpose | Known limit |
|---|---|---|
| T01 | Architecture observations and route expectations | Dependencies do not prove delivery strategy |
| T02 | Source/render readiness and parity | Needs aligned captures |
| T03 | Explicit SPA artifact plan | Trusted local root, not host delivery |
| T04 | Next delivery/cache/model and freshness | Does not read or invalidate cache |
| T05 | Crawl permission/discovery and sitemap reconciliation | Not robots evaluator or crawler |
| T06 | Index/canonical and historical processed evidence | No live index data |
| T07 | Migration mapping and supplied HTTP traces | No fetch or redirect rule generation |
| T08 | Reviewed metadata drafts and literal comparisons | Narrow profile, not semantic/feature validation |
| T09 | Field/lab performance evidence | No actual measurement or causal proof |

T01 can orient subsequent review, but coordinator does not automatically manufacture another module's input from its output. Each runs independently; do not infer that the order creates data dependencies or that unrelated fixtures describe the same site. Security/authorization and critical route hazards are investigated first in actual decision process. Other tools remain standalone: local HTML smoke, R07 link graph, R09 locale matrix, research validation and R08 prioritization. Use these where relevant as separate checks; T10 does not execute them all automatically. No hidden network or shell commands.

### 3. Execute a reproducible local audit
Use scripts/audit_technical.py, fixed allowlist of the nine trusted existing module functions. No subprocess or dynamic imports from user input, arbitrary scripts, filesystem paths in manifest or external provider adapter. T03 alone accepts the explicit CLI artifact-root (trusted directory), checked by existing artifact tool; without it T03 becomes blocked. Run on trusted immutable library/artifacts, not untrusted concurrently changed filesystem. Input max 16 MiB at CLI. Validate duplicate keys, non-finite numbers, exact task coverage, ready inputs vs withheld inputs. Envelope schema_version "1", audit_id, scope, context_ref (reviewed underlying evidence/context), reviewed_revision, tasks object with exactly T01–T09 keys, groups array. Task: state ready/blocked/not_applicable, reason, input_ref nonempty and input object for ready; null input_ref/input otherwise. Module-specific schemas unchanged; retain separate native scope and evidence. CLI rejects malformed envelope. An expected input/IO failure in a selected module is reported as failed with exception class only and does not prevent independent modules being attempted; avoid leaking arbitrary raw errors. Unexpected implementation failures may abort; not an isolation/sandbox mechanism. Module version/layout checked against pinned library; T01 native schema "1", T02–T09 method Txx-v1. Each module records actual status processed/blocked/not_applicable/failed, input and report hashes where available and utility file hash. SHA-256 over deterministic sorted compact JSON for manifest, input/report and signal binding; code hash over exact module file bytes. Hashes identify local snapshots, not authenticity or proof of collection; T03 only verifies existing file paths/size, not artifact content or complete deployed output. Keep revision/context references and trusted checkout separately. Never claim real run tool version if unknown.

Output retains native reports in full (reviewed sanitized inputs only), normalized signals, module counts, independent escalation candidates and reviewed groups. Signal = module, local record_id, JSON pointer to native result, native report hash, binding hash (audit identity/scope/context/revision, module, input reference/hash, report hash and utility file hash), kind review_candidate/deferred, code and detail. T01 explicitly maps its unknown/not-checked codes to deferred; other T02–T08 use native review/deferred lists including T04 samples and T08 capture/plan fields. T09 synthesizes review candidates from non-good field classification and lab regression statuses; null metrics and native deferred checks are deferred. These point to the underlying metric object/status; synthesized code is not a native flag. Preserve native categorization. Escalation markers for existing T01/T04 suspected access exposure remain visible independently of grouping and must be reviewed promptly. Unknown values and deferred flags never turn into a confirmed defect. IDs are local snapshot references, not historical issue IDs, invalidated by input/ref/result/context changes; no cross-run resolution or arbitrary normalization.

### 4. Review and consolidate without hiding evidence
Inspect candidate and native report with underlying source. Reproduce in matched scope where authorized, clarify whether observation is a platform requirement, recommendation, local policy or hypothesis. A candidate from a literal comparison may be valid expected behavior. Conflicting samples require context/revision and real owner investigation, not override by latest file. Do not auto-merge by similar code, URL string, local ID, template name or severity. Example: T02 initial noindex and T06 representative noindex may refer to the same directive on same route only with aligned identity/profile/time and applicable policy; retain both pointers in one reviewed group if confirmed relationship. A wrong canonical and a slow LCP on the same route may need separate owners. No issue count or affected URL reach inferred from signal count.

Operator can rerun with reviewed groups: each group id unique, reviewer/scope/rationale/owner/next_check nonempty, signal_ids nonempty unique exact current review-candidate IDs (no deferred or stale IDs, no signal assigned more than once), severity P0/P1/P2/P3, fit eligible/unknown/excluded, risk and confidence from R08 vocabulary, impact integer 1–5 or null, effort_days reviewed [low,high] or null, depends_on group IDs. All groups are pending; no automatic verified resolution. Retain groups and ungrouped candidates; use rationale to justify actual relationship, reviewed reach and alternatives. Grouping does not verify the rationale, authorization or fix. If context or data changes, re-review references rather than silently reusing them. Use [review inventory](../../templates/technical-audit-review.csv) for fuller issue record, expected/observed evidence, acceptance and rollback. Suspected access exposure is independent escalation even if not grouped or priority judgment differs.

### 5. Prioritize through existing R08
Call existing prioritize_opportunities.prioritize only on reviewed group inputs, never generate severity/impact/effort from alert code or invented score. No group = no triage, all candidates ungrouped. R08 preserves incident/repair/growth/review/investigate/blocked/excluded lanes, dependency validation, uncertainty and risk. Incident/escalation independent; stop unsafe release. Priorities are reviewed project decisions not search penalties. Do not treat ungrouped as low priority, excluded as fixed, or score as ranking probability. Owner review, approved intervention, acceptance checks and rollback required. Keep repair versus search outcomes separate (T06). No automatic fix or bulk edits.

### 6. Report and hand off
Report audit scope and revision, module execution counts, native findings with refs, deferred/blocked reasons, suspected incidents, reviewed group and ungrouped candidates, triage if available, decisions and next checks. Include what was not run and why, actual denominators of collected target records where known, not a synthetic site audit percentage. Native reports may have local counts/limitations. A processed module only means execution, zero candidates does not prove health. Do not infer actual crawl coverage from module count, or search index from technical output. CLI exit 0 = report processed without failed module (blocked/NA/deferred still possible); 2 = report written with one or more failed modules; 1 = envelope/output/group validation error, no valid report. New output path required. All outputs review_required and authorization_required. For release gating see existing operations docs and upcoming T11; do not use exit zero as release permission.

Verify report hashes/pointers, deterministic output at unchanged trusted checkout/inputs, no auto grouping, missing root blocked, malformed module failure preserved, stale/duplicate/deferred signal reference rejection, grouped priority via actual R08 and independent escalation. Compare repository and portable fixture parity. For real audit verify underlying supplied data and authorized artifact/capture, actual site sampling and uncertainty; no real website or provider operation demonstrated by offline suite. E75–E78 public scenarios remain unexecuted as model evaluations.

## MEASURE
Track selected/processed/blocked/NA/failed modules, signal and reviewed group counts separately, underlying observed denominator and deferred evidence, actual reproduction status, time/cost if measured, remediation verification and business/search outcome separately. Repeat with comparable scope and normalized issue identity reviewed by owner; snapshot IDs not longitudinal resolution keys. No automatic issue lifecycle, health score or inferred coverage.

## ADAPT
Small site/targeted issue: select minimal modules and explicitly exclude irrelevant ones. Large site: bounded separate manifests/cohorts, avoid unreviewed merging. Mixed SPA/Next: architecture and route owner review before selecting module-specific projection. No artifact root or provider: mark blocked or NA as appropriate; supplied evidence only. WebsiteBotScroll: optional future versioned adapter after exact contract review; current runner takes independent local inputs, not raw crawler package. Search Console/CrUX: separately authorized evidence and applicable scope. Human-only audit: same review workflow and templates without running tools.

## RECOVER
If invalid module input, do not fabricate replacement. Preserve report including failure, inspect source and native utility validation in authorized local context, correct projection and rerun with new manifest/output. If scope or permissions unclear stop affected collection outside runner. For suspected exposure or critical defect escalate promptly, preserve sanitized evidence, no automatic writes. If grouping stale or conflicting, rerun ungrouped and re-review exact candidates, keep original snapshot. For approved changes record specific acceptance and rollback; current technical recheck is not actual search recovery. Preserve incomplete past results.

### TS02 failure isolation (report method T10-v2)

The input envelope remains schema v1 with exact top-level and task keys. Invalid shared envelope, duplicate JSON keys, non-finite or unencodable text abort before diagnostics. A malformed, stale, conflicting or cyclic reviewed grouping batch is rejected atomically after native diagnostics; output retains every native report and signal, independent suspected exposure references and all ungrouped review candidates. `grouping_status` is `not_requested`, `processed` or `rejected`; `grouping_failure_type` is null or a sanitized exception class. Rejected groups are never echoed or passed to R08 as partial triage. Exit 2 indicates a written partial report with module failure or grouping rejection; exit 1 means input/output failure without a usable new report, and exit 0 means diagnostics processed with no such failure, not approval. Correct rejected groups against current signals on a separate reviewed manifest. Unexpected errors or failures before report creation still require explicit review; not a security sandbox.
