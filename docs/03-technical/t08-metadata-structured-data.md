# T08 — Metadata and structured data automation

Status: initial methodology, typed draft generation and offline literal observation QA. No deployed build, HTML/browser extraction, full JSON-LD expansion, external validators or independent behavioral evaluations executed. Selected sources inspected 2026-11-18. Apply [T02 rendering](t02-javascript-rendering.md), [T06 indexing/canonical](t06-indexing-canonicals.md), [R06 page mapping](../02-research/r06-keyword-to-page-mapping.md) and [R09 multilingual](../02-research/r09-multilingual-search-engineering.md).

## WHAT
Maintain accurate, route-specific metadata and meaningful structured representations of actual public content. Separate document title/description, canonical/index policy, visible headings, social graph, Schema.org entity relationships, search-specific feature eligibility and actual display. Build from reviewed public records with stable entity identity, typed values, evidence and release ownership.

## WHY
Template defaults, stale CMS fields, competing head owners, duplicated or conflicting entity declarations, localization mismatch and invented claims undermine trustworthy representation. Valid JSON alone establishes neither correct vocabulary nor applicability or display. Avoid mass-generated boilerplate and unnecessary metadata infrastructure.

## WHEN / WHEN NOT
Apply to public route templates, dynamic content, locale expansion, metadata or search appearance regressions and justified feature improvements. Retain accurate existing tags and graph where appropriate. Do not add types merely to maximize coverage, create fake ratings/credentials/prices or mark up unrelated or protected content. Do not publish, submit private markup to third-party tools, change indexing policy, install dependencies or modify target code without approval.

## INPUTS
Reviewed content/page registry (purpose, canonical and locale), actual visible primary content and headings, current title/description/share declarations, source and completed response/rendered captures with context, real entity facts and evidence refs (public identity, author, dates, media, offer and reviews where applicable), actual template owners/framework versions, visibility and access review, target feature, platform documentation revision, release and rollback plan. Missing facts are omitted or deferred, never manufactured. Sensitive records stay outside public library and routine evidence exports.

## HOW
### 1. Establish source of truth and intent
Assign stable page and entity IDs from reviewed registry. Separate page identity from entity identity (a brand is not an article; a variant may share an entity but have distinct public representation). Stable @id IRIs, e.g. canonical URL plus #article or a reviewed organization IRI, allow explicit relationships. Do not use sameAs for generic links, directories or speculative identity. Reference verified identity profiles only. Model authorship as actual person/organization, not generic fabricated expert. Keep locale-specific facts, visible claims and publication dates tied to the same content revision. Use schema.org types appropriate to actual subject; don't claim every entity relationship improves search.

### 2. Generate accurate document metadata
Use reviewed title that identifies page task/topic and brand as appropriate. Avoid repetitive boilerplate and stuffed variants; align main visible title, primary language/script and actual content. Description summarizes page-specific value and substantiated facts. No universal title/description character-count gate; assess conciseness, actual display and language, not automatic truncation. Google generates title links and query-dependent snippets from multiple sources, so changes are preferences not guaranteed displayed text. For large inventories, generate from typed approved fields with missing-value policy and editorial sampling. Required local profile fields block draft when absent; for broader deployments define truthful fallback or manual review instead of an empty title or invented attributes. Do not update dates just because deployed code changed.

### 3. Resolve metadata owners and locale
Inspect CMS, static template, framework layout/route and existing head manager before changing. Use supported Next metadata exports or actual React router/head mechanisms (T03/T04); avoid contradictory layout and page tags. For streamed metadata, capture full response and relevant ready DOM, not early prefix. Use R09 intended locale matrix for alternates, preserve actual canonical and locale relationships and Persian/RTL typography; do not transliterate existing paths or infer target locale by script alone. Social fields may use a different accurate title/description. Open Graph basic fields are og:title, og:type, og:image, og:url; description and locale/image details are useful where appropriate. Respect platform-specific locale syntax, multiple image ordering and alt text. Verify actual accessible representative image and share preview separately; no guarantee of search ranking. Social URL should reflect reviewed identity, not untrusted request Host or arbitrary query. Twitter/X card tags and platform validators require current documentation if relevant.

### 4. Select structured data by purpose and feature
| Actual page/entity | Candidate representation | Review before generation |
|---|---|---|
| Organization/home | Organization, WebSite | Real identity, logo, official profiles, applicable homepage guidance |
| Editorial | Article, BlogPosting, NewsArticle | Real author(s), headline, dates and representative media |
| Navigation hierarchy | BreadcrumbList | Actual user navigation paths and list order, not fabricated hierarchy |
| Product detail | Product, Offer where applicable | Real product/variant, accurate price/currency/availability and supported feature requirements |
| Local business | LocalBusiness subtype | Genuine location/contact/hours and feature-specific rules |
| Watch page | VideoObject | Real video, accessible thumbnail, accurate metadata |
| Software/service | Most specific truthful type | Verified functionality and real offer/review data if applicable; not automatically a Google feature |
| FAQ content | FAQPage if appropriate for another use | Google FAQ rich results discontinued from May 7, 2026; no current Google FAQ feature objective |

Check current Search gallery and exact feature guide (including region/device, required/recommended fields and content policies); vocabulary validity is a separate check. Google's Article guide currently lists recommended rather than required properties; our narrow profile is stricter by choice. For Product distinguish product snippets vs merchant listings and actual purchase capability. Never fabricate an offer, aggregateRating, review, author identity, location or JobPosting to unlock a feature. Noindex, access issues and policy restrictions may affect eligibility. Multiple graphs or repeat @id nodes may be legitimate and semantically merge; review conflicting claims and references, don't automatically delete all repeats. Use current vocabulary, appropriately scoped relationships and actual content users can access. Valid entities can exist without Google-supported rich result. Keep feature documentation and deprecation review dated.

For actual feature proposals, use the [structured data feature distinctions](../04-content/structured-data.md): review eligibility for specific products versus category pages, merchant purchase capability and Offer, self-controlled business/organization ratings, desktop versus mobile breadcrumbs and equivalent duplicate pages. Preserve real data and applicable policy separate from local typed-profile output. An appropriate supported feature with missing real required facts is deferred; a valid graph for another consumer is not automatically a Google feature. No local generator or literal check certifies feature eligibility.

### 5. Secure typed generation
Use explicit approved typed public record and a pure generator, not untrusted arbitrary markup or prompt content. Validate type, dates/units/currency, accessible assets, actual claim source and relationships. Prefer structured objects and a supported serializer. JSON.stringify alone does not escape an HTML script end tag. For native application/ld+json script data blocks, serialize valid finite JSON and escape less-than to its JSON unicode escape (and other script-context characters as required); use appropriate escaping for title/attribute contexts separately. Never insert arbitrary raw HTML or fetched instructions. Validate framework/runtime and CSP requirements; do not weaken CSP or allow untrusted script execution. JSON-LD is non-executable data, not a loader. Remote contexts/IRI references are not permission to fetch; offline validator does not resolve them. Scope private evidence and redaction; no secret or signed URLs in generated public tags.

### 6. Offline local profile and capture comparison
Use scripts/audit_metadata.py. It generates a draft from supplied reviewed facts and compares literal observations, never generates facts or publishes markup. Envelope schema_version "1", scope, pages (1–500 unique IDs). Each page id, expected_context (reviewed route/revision/locale/representation label), plan, source, rendered. Plan reviewed=true (operator attestation, not independently verified approval), facts_ref, title, description, share_title, share_description, locale (nonempty reviewed language label; BCP47 validity external), canonical, share_image (reviewed absolute HTTP(S) URLs, no fragment/credentials), article=null or object: type Article/BlogPosting, headline, author_type Person/Organization, author_name, image, date_published (YYYY-MM-DD), date_modified (same calendar format or null, not earlier), facts_ref. This intentionally narrow profile uses one author and image, one date granularity and website/article OG types; real multi-author, timestamped, product, other type or complex graph workflows require additional approved generation, not data loss. No automatic language detection. Output draft contains strings, optional JSON-LD object (@id canonical+#article) and script-context-safe JSON text. Metadata values are NOT escaped HTML; use actual framework text/attribute escaping.

Capture: status complete/partial/failed/not_collected, context_id, evidence_ref (null only if not_collected), metadata exact groups title, description, canonical, og:title, og:description, og:type, og:url, og:image; each string array (max 100) or null. jsonld_blocks array of at most 50 raw extracted script texts each at most 250,000 characters, or null. Failed/uncollected must have null groups/blocks. Complete means assessed relevant groups of completed source or readiness-established DOM; individual unknowns null. Partial prefixes don't establish absence. Capture context must match reviewed plan; operator verifies actual comparability, not tool. Compare each capture against plan independently; not a browser/source comparison engine. Arrays preserve duplicates/malformed strings; repeated or differing values review, not universal invalidity (multiple OG images may be legitimate). Same-locale exact planned title reuse across distinct canonical values flagged for review, not automatic duplicate-content finding. Source initial absence may be intentional for JS-generated fields; review T02/T04. Canonical eligibility checks T06 separately.

JSON text is parsed with duplicate key/non-finite rejection; syntax errors flagged without asserting entity absence. Recognized subset: direct object with explicit https://schema.org or https://schema.org/ context, or simple wrapper with only @context and @graph array of nodes. No context expansion, alias handling, reference resolution, RDFa/Microdata, general JSON-LD semantics or nested graph merging. Unsupported/ambiguous shapes defer claims; exact @id candidates and expected literal values compared in recognized scope. A valid alternative encoding may differ; all findings require review. Additional properties require semantic review, not automatic deletion. No universal validation from zero findings; output includes limitations. New output path, exit zero means processed. See [fixture](../../examples/metadata/README.md).

### 7. Validate in layers and roll out
1. Check reviewed facts, actual visible content, locale and safe serialization.
2. Validate generated and actual source/full response/ready DOM markup, owners, duplicates and links (T02/T06).
3. Use Schema Markup Validator or approved vocabulary validator for appropriate representations; use Google Rich Results Test for supported features, record actual errors/warnings, not all optional warnings as blockers. These are separate from local literal checks.
4. Review feature-specific content eligibility, real claims, crawl/access and image/resource response; live check only under approved scope. No private evidence uploads. Use authorized Search Console reports and processed evidence (T06) for actual search appearance, separate from test eligibility; valid markup never guarantees display.
5. Stage representative templates/locales, compare actual metadata and preview, verify UI/accessibility/rollbacks. Use a bounded approved release; monitor real outcomes, no fabricated performance numbers.

## VERIFY
Check concrete route and revision, approved title/description/canonical, source and ready DOM, actual share preview, safe script text with injection regression fixtures, visible fact parity, actual representative images, applicable feature requirements and external test scope/date. Test missing CMS fields, translations, duplicate owners, layout inheritance, update/failure/cached content, malformed blocks and unauthorized payload protection. Keep user experience and index policy unchanged unless approved. E67–E70 are public scenarios, not independently measured agent outcomes.

## MEASURE
Use scope and denominator: reviewed public pages, generated drafts, actual checked captures/fields, deferred counts, feature-validation outputs by category, verified semantic issues and release regressions. Track search appearance, impressions/CTR and actual click/conversion outcomes by comparable query/page/locale/device cohorts separately. Do not attribute changes solely to metadata or compare different reporting scopes. No ranking/display guarantee.

## ADAPT
Static/SSR: reuse authoritative content record at build/runtime. CSR: verify actual ready metadata and direct route, avoid generic source conflicts. Next streaming: compare completed response with matched readiness. Persian/ multilingual: natural localized titles/description, preserve Unicode, actual hreflang and entity relationships. Product/large catalogs: approved product feed/visible price variants, cache consistency, feature-specific validation, no fake defaults. No eligible rich feature: useful accurate entity markup optional, no-change acceptable. Unknown content or extraction: defer. No provider/validator: record local checks only.

## RECOVER
If metadata conflicts or misleading claims released, stop affected rollout, identify generator/owner and revert or narrowly correct approved change. Preserve correct public identity and intended index policy, refresh authorized caches where required, recheck actual content/metadata/graphs and localized cohorts. For exposure/security stop and escalate separately; never rely on noindex. Record external tests only if performed, distinguish processed-state lag. Do not delete all graph markup or repeatedly request recrawls to force appearance.

## EXTERNAL PROVIDER EVIDENCE REQUIREMENTS
Approved WebsiteBotScroll or compatible provider may supply raw source/complete-response and ready rendered title, descriptions, canonical, applicable directives, social fields (ordered duplicates), headings, language, structured-data format/script/extraction context, parsing outcomes, raw/resolved ID/property evidence where allowed, resource/image responses, observation refs/timestamps/method/version/coverage and failures. Preserve malformed declarations and per-group collection status. Avoid exporting entire sensitive markup or private content. Project owner supplies actual reviewed facts, intended identity, locale, semantic equivalence and feature objective. Search-platform observations are separate; crawler cannot guarantee feature eligibility or actual display. Shared 0.1.0 contract pending exact schema review; no provider adapter, network extraction, API or MCP.
