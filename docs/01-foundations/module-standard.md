# Universal module authoring standard

Every workflow or knowledge module added or revised should be actionable by an agent and separately useful to a human. Use the following sections where applicable; mark irrelevant ones N/A with reason. Legacy documents are migrated as touched, not claimed compliant already.

| Section | Requirement |
|---|---|
| WHAT | Definition, boundary, supported website types |
| WHY | Mechanism, user/business value, evidence strength and limitations |
| WHEN | Entry conditions, task triggers and dependencies |
| WHEN NOT | Exclusions, risks, counterexamples and when no change is best |
| INPUTS | Required and optional evidence, authority and tool capabilities |
| HOW | Ordered decision steps, alternatives and actionable patterns |
| VERIFY | Exact acceptance tests with expected result; separate static/live/indexed checks |
| MEASURE | Outcome, baseline, comparison, uncertainty and evaluation timing |
| ADAPT | Different stacks, markets, site types, scale and missing capabilities |
| RECOVER | Failure conditions, safe rollback and escalation paths |
| OUTPUTS | Artifacts, decision records, test evidence and unresolved questions |
| SOURCES | Primary links, date checked, claim scope, update triggers and local policy distinction |

Distinguish platform rules from project conventions and experiments. No guaranteed rankings, fabricated volumes, made-up sources, universal numeric scores or unverified tool availability. A good module contains branches for missing data and counterexamples rather than unconditional actions.

## Review checklist

1. Can an unfamiliar agent identify when this module applies without relying on any one brand?
2. Are the evidence, alternatives, decision and result distinguishable?
3. Are test methods reproducible with known tools or clearly optional?
4. Is no-change a valid outcome? Are privacy/authorization, failure and recovery addressed?
5. Is the material current, clearly sourced and consistent with existing references?
6. Does a new or changed high-risk procedure have at least one normal case and one adverse case in the evaluation suite?
7. Do navigation and package checks pass, and have private project data and secrets been excluded?

Author in the canonical library, not in generated skill distributions. Log material decisions, source changes, tests and evaluation results in Git. See [decision engine](../../decision-engine/README.md) and [evaluation guide](../../evaluations/README.md).
