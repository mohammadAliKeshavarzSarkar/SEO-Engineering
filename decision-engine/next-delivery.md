# Next.js delivery and freshness decision protocol

Use [T04](../docs/03-technical/t04-nextjs-hybrid.md) after T01/T02. Establish installed version, router ownership, cache model, deployment and concrete route purpose. Retain verified working delivery. If static export has runtime requirements, review supported host/runtime or remove only the unjustified feature; never promise ISR on a static host. If missing dynamic routes, check real published params, fallback policy/build and status before changing URLs. If content is stale, define an actual target revision and deadline, compare matched samples, inspect upstream/server/host/client scopes and failure/invalidation evidence; don't infer cause from cache header or time alone. If Cache Components is enabled, use installed-version explicit cache scopes rather than previous route segment settings. If a streaming error follows HTTP 200, distinguish committed status, rendered error, applicable robots evidence and actual search processed state. If metadata differs, inspect route/layout/file owner and completed stream rather than partial head alone. If private payload is suspected, stop release and escalate to authorized incident response; noindex is not access control. Choose smallest reversible fix, test authorized route matrix, cache/variant freshness and UX, preserve evidence, report unknowns and rollback. Use [Next patterns](../implementation-patterns/nextjs-delivery.md). Provider-independent, no crawler/API requirement.
