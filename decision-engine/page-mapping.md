# Task-to-page decision protocol

Use after [R06](../docs/02-research/r06-keyword-to-page-mapping.md) with R03–R05 evidence. Read-only planning by default.

1. Confirm task, locale, real audience/offering, evidence and expected index policy. Exclude unsupported tasks; defer where uncertain.
2. Check current page registry. Consider all relevant existing pages and separate task fit from technical eligibility. Retain appropriate existing URLs; repair faults separately.
3. If an adequate page exists, assign it as intended primary for the resolved mapping unit. If incomplete, propose improvement. Optional supporting pages are independently useful; preserve their URLs when distinct.
4. If distinct unmet task is substantiated, compare new page/tool versus extending current page. Propose new only with independent value, evidence, feasible owner and links. If mixed/unresolved, retain multiple candidates and no forced primary.
5. If multiple current URLs appear for a query, inspect their purposes, content equivalence, aligned query/page evidence and technical state. Keep different useful content. For true duplicates consider canonical preferences if retained, or relevant permanent redirects if retiring; noindex for separate nonindexability, not canonicalization. Changes to URLs require separate authorization, migration map and rollback.
6. Record the primary/supporting relationship, decision state, source evidence, alternatives and page requirements. A selected primary is a plan; it does not predict engine-selected canonical or ranking.
7. Validate registry relations and release plan; route page briefs to R07/R08. Do not publish or migrate without approval.

Use [task-page mapping](../templates/task-page-mapping.csv), [page registry](../templates/page-registry.csv) and [page brief](../templates/page-seo-brief.md). For approved URL changes consult [migration guidance](../docs/03-technical/urls-and-migrations.md). A failed or unknown evidence gate should produce a bounded next investigation, not invented results.
